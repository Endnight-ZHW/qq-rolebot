# 工具分类权限

在「会话管理 → 权限中心 → 工具授权」中选择工具，点击「配置」，将授权模式设为「按身份配置」。管理员包括当前 QQ 群主、群管理员和系统设置中的管理员 QQ；自定义权限组和“本群协管”角色不代表 QQ 管理员身份。

| 配置示例 | 普通成员 | 管理员 |
| --- | --- | --- |
| 普通成员只能改自己头衔 | 仅限自己 | 本群所有成员 |
| 只有管理员可以改名片 | 禁止使用 | 本群所有成员 |
| 所有人只能撤回本人消息 | 仅限自己 | 仅限自己 |
| 公告只供管理员使用 | 禁止使用 | 允许使用 |

快捷按钮同时在草稿里开启工具和用户请求，保存后生效。机器人自主使用是独立开关。普通成员与管理员各自遵循选定范围，管理员不会再叠加普通成员范围。

分类规则既提供基础授权，也是该工具的统一上限。个人和角色的单项允许不能扩大范围；单项禁止、账号禁用、授权有效期、保护名单及禁言时长限制仍生效。后台管理员同样遵守新工具规则，后台登录及原有应急指令保留。

仅限自己支持群头衔、群名片、成员资料、禁言、解禁、移出群聊和撤回。本人以绑定的真实请求者 QQ 为准；撤回还核实原消息作者。其他工具只提供允许、禁止，不把历史检索中的发言人筛选等参数误当成个人操作目标。提醒和定时任务继续只管理本人创建的任务。

QQ群身份通过当前群成员查询核实，工具实际执行、耗时复核后、延迟发送前重新核验。核验失败停止执行，反馈为身份尚未核实，不宣称用户没有权限。权限通过不代表 QQ 平台一定允许；例如头衔仍要求机器人为群主且相关服务可用。

## 兼容与接口

`Policy.request_access` 缺失或为 `null` 时使用原有账号授权，升级不会改写三个群的权限。示例：

```json
{"member_title":{"enabled":true,"user_enabled":true,"request_access":{"member":"self","admin":"all"}}}
```

通过 `PUT /api/v1/groups/{scope}/tools?expected_revision={group.revision}` 保存。修改分类规则必须提供当前版本；不一致返回 409，前端保留草稿。旧客户端不提交新字段时保留已保存规则。`GET /api/v1/tools` 的 `supported_scopes` 表明合法取值；不支持个人目标的工具提交 `self` 返回 422。

`GET /api/v1/permissions/{scope}/effective/{qq}` 的 `tools` 返回 `mode`、`target_scope`、`identity_source`、`available`、`reason` 和 `error_code`。这是使用资格预览；具体目标保护、时长、限频和平台条件在调用时再校验。旧模式下，完整撤回和本人撤回仍分别展示，保留已有接口语义。

旧的“继承 QQ 管理员”开关只控制暂停、恢复、紧急停用等原有指令；新分类工具始终依据真实群身份和后台管理员名单。模型只读取服务生成的权限范围，不能创建授权。

权限诊断的 `limits` 汇总工具与账号／权限组的有效禁言时长，保留各自来源；保护名单区分工具、账号／权限组与默认管理保护。默认保护的本人撤回例外仍需核实真实作者，QQ 平台等级限制继续在执行时检查。模型上下文的 `requester_access` 对旧账号授权和新分类授权均提供明确原因；`available` 只表示当前请求者的请求许可，不代表机器人 QQ 身份或操作一定成功。

禁言与解禁分别保存。权限中心根据草稿提示“解禁关闭”“仍沿用账号授权”或“解禁范围更小”，诊断页按指定 QQ 的已保存权限再次提示；不会自动联动开关、复制授权或扩大范围。普通成员被禁言后可能无法发出解禁请求，应考虑等待到期或由管理员处理。

文字／表情准备成功后，发送计划带有服务生成的执行编号。延迟发送前重新核验原始调用方式、实际请求者及共享受众、工具状态和额度；兼容工具接口更新也会生效。额度检查排除同一准备记录已占用的一个名额，不重复占额、不提高上限；真实发送限频和未知结果不重发保持独立。

工具结果新增 `phase` 与 `submitted`，区分授权、QQ 身份预检、调用、结果核实与消息准备。预检失败明确表示未提交；提交后的回执不明才按结果未知处理。时长、每小时上限、用户请求关闭、服务不可用等原因使用各自错误码。仅准备了文字／表情不能作为管理操作的执行证据；条件玩笑不构成未来自动处罚任务。

## 发布与回退

升级前在隔离环境验证。`ops/release.py stage` 会保存现有镜像、数据库和源码，另外从一致性数据库备份生成 `permissions.json`，并检查候选镜像以 UID/GID 1001 导入代码及校验源码哈希。代码复制为服务用户所有，避免仅以 root 通过测试却不能启动。

权限恢复工具只修改 `group.tools` 与 `qq_access`，递增版本并记录恢复审计，保留升级后的聊天、记忆、群名等其他数据。以下命令在服务器执行，实际路径替换为本次备份目录；先停止应用，检查预览，再执行恢复并启动目标镜像：

```sh
python3 ops/permission_backup.py restore --database data/app.sqlite --snapshot upgrade-backups/本次发布/permissions.json
python3 ops/permission_backup.py restore --database data/app.sqlite --snapshot upgrade-backups/本次发布/permissions.json --apply
```

若上线后未启用任何分类规则，代码回退即可恢复旧行为。已经使用新规则时，必须结合权限快照恢复，不能让旧代码忽略新范围后继续运行。完整数据库备份保留用于灾难恢复，不用于日常回退。

## 主页点赞与群内戳一戳

本版本新增两项群互动工具，默认关闭且不自主调用；在各群「工具与权限」开启后，选择普通成员与管理员的范围。现有工具和账号授权保持原样。

| 工具 | 默认参数与限制 | 平台调用 |
| --- | --- | --- |
| 主页点赞 `profile_like` | 未指定数量时按单次上限和当天剩余额度提交；默认单次 10、每日累计 10 赞；可在后台调整程序上限，跨群共用累计数量，QQ 实际接受数量以回执为准 | `send_like(user_id,times)` |
| 群内戳一戳 `member_poke` | 一次一下；同一目标默认冷却 60 秒，后台可设 10～86400 秒，跨群共用 | `group_poke(group_id,user_id)` |

两项均支持「仅限自己 / 本群所有成员」，目标必须通过当前群成员核验，机器人无需是群管理员。点赞针对 QQ 主页，不是群消息的表情回应；戳一戳只发生在当前群，不自动回戳，也不切换到私聊。

点赞限额按接口已接受的数量累计，北京时间零点重置；这是后台程序额度，QQ 实际允许的数量仍由 QQ 决定。例如当天已提交 1 赞，再明确请求补足时只提交 9 赞。用户没说具体赞数时省略 `times` 或传 `null`，“点一下”不等于指定 1 赞；明确请求 1 赞仍只提交 1。已有群的单次上限原样保留，缺失的每日上限默认 10。

调用前原子预留，执行中禁止并发提交。QQ 明确因对方权限拒绝或请求尚未发出时不消耗赞数，冷却 30 秒后可由新用户请求重试；明确返回平台当日额度用尽时当天停止。超时、中断和无法判断是否部分成功的错误阻止当天补发。戳一戳仍按原冷却限制，失败不自动重试。不会承诺稍后或明天自动补赞。

点赞记录使用当前累计计数格式，延迟回执仍可核实已提交数量；没有可靠回执时保留结果未知的限制。同一请求通过执行记录去重，刷新网页或服务重启不会重放。后台保留每小时上限、保护名单和紧急停用。接口已接受与客户端显示已核实分别标识；不独立保证赞数或动画显示。QQ 拒绝、权限不足、身份不明、本地限额和超时未知分别处理，不根据通用错误码猜测上游额度。准备文字或表情成功也不能掩盖点赞失败。

旧记录恢复按真实聊天中的 `send_like` 请求、目标 QQ 和对应 `echo` 回执匹配，不再受最新两条追踪记录的限制。记忆整理和模型回放不能充当执行证据，后续本地拒绝也不能遮盖原来的成功记录。点赞超时后额外保留最多 120 秒的回执关联；收到迟到的明确回执时，只记录证据，不主动重发。下一次用户明确请求会据此重新计算剩余额度；仍无回执或证据冲突时继续防止重复提交。

同一条用户消息不能通过更换参数或理由再次提交点赞；确需重试时由新的真实消息发起。即便迟到回执补齐了结果，也不会将原消息自动重放。

## 引用与简短确认

工具来源核对保留近期聊天，同时按当前真实 QQ 消息的引用编号补齐原文、机器人答复对应的用户请求，以及期间该请求者的发言。超过普通 10 分钟窗口的明确引用可以提供操作背景。优先使用本地记录；缺失的直接引用最多通过两次只读 `get_msg` 核验群、消息编号、真实作者和时间，原文只留在本轮，不导入聊天或业务记忆。

“再试试”“就按这个来”在操作、对象明确且没有取消冲突时可延续请求。当前发言者始终重新检查权限；引用别人的许可不能借用其身份。已遗忘、停止记忆、跨群、跨角色、重置前或时间不符的本地记录不能通过补取恢复。模型核对后及执行前重新检查引用来源，核对失败应说明缺少的操作信息，不再笼统地称为后台或账号权限拦截。

接口依据：[NapCat 官方接口文档](https://napneko.github.io/onebot/api)。回归测试模拟 QQ 返回，不实际给群友点赞或戳一戳。
