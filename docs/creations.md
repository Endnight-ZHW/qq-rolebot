# 作品制作

后台「任务中心 → 作品制作」管理 PNG、GIF 和无声 MP4；源码只作为文本/下载展示。制作工具与其他工具一样使用群开关、真实请求者权限和独立自主开关。所有新工具默认关闭，普通聊天保持原有模型、上下文预算、参与概率和发送方式。

## 流程

`creation_create` 只入队并返回任务编号。独立 worker 调用 `creation` 路线（缺省沿用聊天模型，high，最多 65,536 输出），向宿主调度器提交 Python 或 HTML。制作模型单次响应等待上限为 300 秒，独立于普通聊天的 65 秒；不会修改共享客户端的超时设置。调度器运行不联网的临时容器，逐帧渲染，再用另一个干净容器检查媒体格式；模型查看真实静态图或带时间标签的动画采样图，最多修复三次、每次重新检查。每任务最多十六次真实模型请求，总制作时间独立限额；制作请求不自动重试网络错误或未知结果。明确的输出截断会进入有限修复，并保留截断原因，不仅报 JSON 解析异常。

`creation_status` 查询自己的任务，`creation_cancel` 取消自己的任务。明确的“取消制作”“不用画了”等本人消息也会中止本人当前任务；无关聊天不取消明确委托。后台管理员可管理全部任务。追改通过 `parent_job_id`，只使用同群、同角色、同请求者仍保留的作品。群友请求被拒绝不能改走自主制作。

图表资料放在 `data`，携带来源、日期、单位、测试条件；工具提示和制作/检查提示要求缺失项标未知，不能补造性能数据。素材只接受当前可读取的 `img_…`、角色库 `ref_…`、`sticker:…` 及已上传的 `art:…`，不接受任意本地路径或 URL。

成功后发送层仅使用登记的产物编号及随机短期内部媒体地址，文字和每个媒体分别发送。GIF 使用动画表情类型；MP4 带首帧预览。结果未知不自动重发。制作 worker 不持有群聊锁，创建、开始、模型调用后、实际发送及发送等待结束都复核来源和权限。

## 制作工作区与检查

借鉴 [DeepSeek Harness 的轮次、工具结果与历史投影设计](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.zh.md)，制作任务保留同一段编写历史，包括工具结果、原生模型消息、有效源码及逐轮反馈；不引入整个插件框架，也不开放宿主 shell。素材查询整个任务最多两轮，返回可编辑 SVG 原文，按需读取，不自动遍历素材。

MP4/三维/矩阵任务先用一次文本模型请求确定短蓝图（16384 输出上限，解析失败不重做计划），再按既定方案实现。第一版可附带短的 `design` 构图/分层/时间线说明。后续支持完整代码或唯一匹配的 `patches: [{old, new}]`，每轮最多 12 处，修补不匹配或 Python 语法错误会在渲染前反馈，代码仍只在隔离容器执行。编写和检查都保留 65536 输出上限，走原有 high 制作路线。已知的检查 JSON 异常/截断只补一次检查，不重新生成代码；网络未知结果不自动重试。素材工具阶段完整保留原生推理信息，产出有效初稿后修补阶段关闭素材工具，只保留可见源码与反馈，不把无需重传的长推理重复计入上下文预算；较早图片按上限投影，最新成品优先。后台展示阶段调用次数、修补轮数、方案和完整检查意见。

动画额外生成 `timeline.png`：分成 12 个时间区间，流式选择各区间帧间变化较大的一帧并标注时间，避免只看首、中、末三个相同周期相位。采样仍不是每帧全量视觉审查，提示词要求说明未覆盖的细节与不确定性。检查模型还可按需调用 `creation_inspect` 对本任务图片裁剪或查看 GIF 的真实指定帧，每轮最多两次查看；不能读取其他任务、任意路径或执行代码。采样图不发群，仅用于检查和后台源记录；逐帧处理只保留上一张低分辨率差分图和一张有界联系图。

质量检查同时评估主体表达、构图、工艺、文字和运动，记录具体位置及修补建议，不把“能识别主体”当作精致程度合格，也不按个人审美随意拒绝。小型 2×2／3×3 显式矩阵先用分数运算核算行列式与体积倍数，把可计算事实交给制作与检查两侧；原始资料保留，不将模型整理出来的错误数字当作事实。

## 隔离和资源

- 调度器是宿主 root 服务，只向 app 暴露 0600、UID 1001 的 Unix socket；app 和任务容器都没有 Docker socket。调度器代码安装在 root 所有的 `/opt/qq-rolebot-render`。接口不能指定镜像、命令或宿主挂载。
- 任务使用固定镜像 ID、UID/GID 1001、只读根、无网络、无额外 capabilities、no-new-privileges、1–2 GiB 自适应内存和同等 memory-swap（禁用 swap），上限仍为 2 GiB、2 CPU、128 PIDs。`/work` 256 MiB、`/tmp` 64 MiB、共享内存 128 MiB；单文件系统写入硬上限 32 MiB。
- Chromium 显式开启沙箱，Three.js 使用软件 WebGL2，不开放 GPU。seccomp 基于 Playwright v1.64.0 官方配置，额外允许 Chromium 在自己的 user namespace 内执行 `chroot`，容器宿主 capabilities 仍全部移除；不使用 `--no-sandbox` 或 SYS_ADMIN。
- 输出进程完成后冻结整个容器。调度器通过固定目录文件描述符和 `O_NOFOLLOW` 复制精确白名单内的普通文件，拒绝链接、异常路径和额外文件。独立校验器检查 MIME、像素、帧率、帧数、时长、完整解码、SHA-256；不会导入生成代码。
- 全局 1 个任务；等候最多 8 个；每人最多 1 个未结束任务；默认排队和制作各 600 秒，后台最高可设 900 秒。单次渲染容器仍不超过 180 秒，模型调用和检查计入总制作时间。启动为宿主保留 768 MiB，根据剩余可用内存按 256 MiB 档选择 1–2 GiB 的容器限制；最低启动可用内存为 1792 MiB，运行时低于 768 MiB 仍终止任务。内存不足、渲染器忙和不可用会记录实际等待原因，排队超时保留原因。
- PNG 最多 3 张、合计最多 800 万像素、最长边 4096、每张 8 MiB；GIF 最长 8 秒/12fps/640 边/8 MiB；MP4 最长 20 秒/24fps/720p/24 MiB/无声 H.264。动画宽高为偶数。
- 明确请求缺省每群 24 次/小时；自主制作另限 4 次/小时、相隔至少 300 秒。后台可调整业务额度，不能突破容器硬上限。模型超时、网络断开、排队超时、总制作超时和画面失败分别反馈，不把网络问题归因于内容复杂。

## 保存、恢复和隐私

源文件和成品在 `/data/creations/<job_id>`，元数据在现有 objects 表的 `creation_job`，设置在 `creation_config/global`。保留 7 天、总额度 10 GiB，收藏子额度 4 GiB；接单预留 96 MiB，包括源素材和最坏输出。优先清理过期作品；不自动删除未过期或收藏作品腾空间。

以上为新默认值。已有持久化制作配置及显式 `creation` 路线不被代码默认值覆盖；升级时备份当前配置，再仅调整获批的制作额度与制作输出上限，保留普通聊天、决策、记忆路线、群开关和权限。回退恢复升级前这些字段，不恢复整库。

制作设置新增独立 `context_tokens=256000` 总预算，按保守字符及图片估算输入，再加预留模型输出检查；同时遵守实际模型上下文容量和图片传输限制。以前制作直接检查模型容量，没有独立的 128000 制作预算。普通聊天的三个 128000 不受此设置影响。旧客户端保存时省略该新字段会保留当前值；超预算在付费提交前拒绝并明确说明，不静默截断源码或证据。

作品检查先记录画面中可见的主体、动作和位置关系，再区分核心缺失/事实错误与可选美化。Q版几何比例、圆形手脚等不按写实标准否决；主内容缺失、看不清或数值错误仍拒绝。修复请求带上实际上一版预览与累计修复意见，后续解析/渲染错误不能覆盖未解决的画面问题。制作代码 JSON 中仅对字符串内漏转义的换行、回车、制表符做无损转义修复；不猜补缺失引号或截断代码，不改变普通聊天/工具 JSON 解析规则，也不消耗额外模型调用。

停止记忆成员的任务输入和成品仅临时保存，发送结束即清理；宿主渲染工作区为 tmpfs，接收临时文件使用 app 的 `/tmp` tmpfs。遗忘会取消相关任务、删除源文件、成品、预览缓存和媒体凭证，收藏无例外。

用户明确取消与后台取消保存各自原因；工作进程中断不冒充用户取消，也不覆盖已记录的取消原因。重启后队列保留；编写、渲染和检查中的任务标记中断，不重新付费；待发送成品重新核验，发送中则标记结果未知。调度器重启只清理自己的 owner 标签容器及 UUID 导出目录。调度器完成导出缓存最多保留十分钟，配额 128 MiB；app 接收后立即请求删除。制作容器退出时全部临时帧一起回收。

## 制作服务安装

制作服务部署到具备 Docker 和 user namespace 支持的 Linux 主机；应用、调度器与渲染镜像须来自同一版本，当前协议为 2。

1. 构建 `docker build -f rendering/Dockerfile -t qq-rolebot-renderer:local .`，记录 `docker image inspect qq-rolebot-renderer:local --format '{{.Id}}'` 输出的不可变镜像 ID。
2. 在 root 所有的 `/opt/qq-rolebot-render` 下放置 `rendering` 目录与 `backend/rolebot/creation_contract.py`，保持原目录关系。用 `install -m 644 rendering/qq-rolebot-render.service /etc/systemd/system/qq-rolebot-render.service` 安装单元。
3. 创建仅 root 可写的 `/etc/qq-rolebot-render.env`，内容为 `RENDER_IMAGE=sha256:<已核验的镜像ID>`；运行 `systemctl daemon-reload` 和 `systemctl enable --now qq-rolebot-render`。调度器使用 Python 标准库和宿主 Docker CLI，不需要模型密钥。
4. 应用挂载 `/run/qq-rolebot-render`，检查后台渲染器连接状态。确认 `CREATION_MEDIA_BASE` 为 NapCat 可访问的应用内网地址；媒体路由不得通过公网网关暴露。
5. 在后台开启制作服务，并按需要配置各群的制作工具、用户范围和自主使用；没有授权时不执行制作。素材库初始为空，可按需上传。

升级前备份镜像、应用与调度器代码、环境文件和权限配置；停止正在运行的制作后配套切换。检查应用健康、调度器状态、协议及权限，测试发送只在自己授权的测试群进行。仅做应用升级时不要重新初始化群工具权限。

`ops/creation_release.py enable` 是需要明确指定群 scope 的可选自动安装与授权工具，会为这些群开启制作及自主制作；只需要安装环境时使用上面的手动步骤。`restore` 只恢复该次功能快照，应用镜像另行回退。回退不恢复整份聊天数据库，保留后续聊天与无关权限更新。
